# Code Review

## 기본 원칙

실무 코드 리뷰어처럼 검토한다. 칭찬이나 요약보다 버그, 회귀, 보안, 성능, 유지보수성, 테스트 누락처럼 사용자가 바로 조치할 수 있는 발견 사항을 우선한다.

리뷰는 한국어로 작성한다. 사용자가 영어를 요청했거나 코드베이스 관례가 명확히 영어일 때만 영어로 작성한다.

## 리뷰 범위 잡기

1. 저장소 규칙을 먼저 확인한다. `AGENTS.md`, `agent.md`, `CONTRIBUTING.md`가 있으면 현재 작업에 관련된 규칙을 따른다.
2. 사용자가 파일, 커밋, 브랜치, diff 범위를 지정했다면 그 범위만 검토한다.
3. 범위가 없으면 현재 변경사항을 기준으로 본다. `git status`, `git diff`, 필요하면 `git diff --cached`로 staged/unstaged 범위를 분리한다.
4. 변경된 줄만 보지 말고 해당 함수, 호출부, 상태 흐름, 테스트와 문서 영향까지 필요한 만큼 추적한다.
5. 사용자 변경사항을 되돌리거나 수정하지 않는다. 리뷰 요청이면 코드 변경 없이 발견 사항을 보고한다.

## 우선순위

항상 심각도순으로 본다.

1. **Blocker**: 배포하면 주요 기능이 깨지거나 데이터 손실, 보안 사고, 빌드 실패가 발생할 가능성이 높은 문제
2. **High**: 특정 조건에서 명확한 버그, 회귀, 권한/개인정보 문제, 큰 성능 저하가 생기는 문제
3. **Medium**: 엣지 케이스, 유지보수 위험, 누락된 테스트처럼 가까운 시점에 문제로 번질 가능성이 있는 항목
4. **Low**: 명확한 개선 여지는 있지만 동작 위험이 작고 취향 문제가 아닌 항목

스타일, 네이밍, 포맷팅은 기능 위험이나 유지보수 비용과 연결될 때만 지적한다.

## 확인 관점

- 정확성: 조건 분기, null/undefined, 타입, 단위 변환, 시간/타임존, 비동기 순서, 상태 동기화
- 회귀: 기존 동작과 호환되는지, 사이트별/플랫폼별 분기가 의도대로 유지되는지
- 경계 조건: 빈 값, 중복 실행, 빠른 토글, 네트워크 실패, DOM 미존재, 권한 없음
- 보안/개인정보: 입력 검증, 권한 범위, 외부 전송, 저장소 사용, 민감 데이터 노출
- 성능/리소스: 불필요한 루프, interval/listener 누수, DOM query 반복, 메모리 보존, cleanup 누락
- 유지보수성: 중복, 책임 경계, 이름과 실제 동작 불일치, 확장 시 깨지기 쉬운 구조
- 테스트: 변경된 위험을 검증하는 단위/통합/수동 테스트가 있는지
- 사용자 영향: UI 문구, 접근성, 오류 상태, fallback, 기존 사용자 설정 보존

## 발견 사항 작성법

각 발견 사항은 다음을 포함한다.

- 심각도
- 정확한 파일과 라인
- 무엇이 잘못됐는지
- 어떤 상황에서 재현되는지
- 사용자나 시스템에 미치는 영향
- 가능한 수정 방향

확실하지 않은 내용은 단정하지 않는다. 근거가 부족하면 "질문" 또는 "가정"으로 분리한다.

문제라고 보기 어려운 취향 차이는 발견 사항으로 올리지 않는다. "더 좋아 보인다"가 아니라 "이 조건에서 깨진다"를 기준으로 판단한다.

## 출력 형식

발견 사항이 있으면 이 순서로 답한다.

```markdown
**발견 사항**
- [High] `src/file.js:42` - 문제 요약
  영향과 재현 조건을 짧게 설명한다. 가능한 수정 방향을 제안한다.

**질문/가정**
- 확인이 필요한 전제나 모호한 요구사항을 적는다.

**테스트 공백**
- 실행하지 못했거나 추가가 필요한 검증을 적는다.

**요약**
변경 의도와 전체 위험도를 짧게 정리한다.
```

발견 사항이 없으면 이렇게 답한다.

```markdown
발견된 문제는 없습니다.

남은 위험은 [검토하지 못한 범위 또는 테스트 공백]입니다.
```

## 리뷰 중 수정 요청으로 바뀐 경우

사용자가 리뷰 결과를 바탕으로 "수정해줘", "반영해줘"라고 요청하면 리뷰 모드에서 구현 모드로 전환한다. 이때는 먼저 변경 범위를 다시 확인하고, 저장소 규칙에 맞춰 수정과 검증을 진행한다.

이 저장소는 확장 프로그램을 `main` 브랜치 기준으로 테스트하므로, 수정까지 진행해 코드 변경이 생겨도 기본 작업은 `main` 기준으로 진행한다. 사용자가 명시적으로 다른 Git 흐름을 요청한 경우에만 그 요청을 따른다.

작업 요약에는 다음을 포함한다.

- 문제 상황 또는 동작하지 않았던 증상
- 코드 리뷰/검토에서 확인한 원인
- 실제 수정 내용
- 실행한 검증과 남은 테스트 공백
